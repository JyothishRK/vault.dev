Benefits:
- Prevents DoS attacks - intentional and unintentional
- Cost reduction
- Prevents server from overloads

Location of rate-limiter:
- Client side: Unreliable since it can be forged with malicious actor.
- Server side
- Alternative:- A middleware service that throttles the requests to the server

- Usually rate-limiting is implemented within the API gateway.
- API Gateway offers:
    * Rate limiting
    * SSL termination
    * Authentication
    * IP Whitelisting
    * Servicing Static content.....

Algorithms for rate limiting:
- Token bucket
- Leaking bucket
- Fixed window counter
- Sliding window log
- Sliding window counter

 ^pTQBpG3p

- Token bucket is a container with pre-defined capacity.
- Tokens are put in the bucket at preset rates periodically.
- Each request consumes 1 token:
    - If tokens are present, request goes through.
    - Else request is dropped.
- Token bucket has 2 parameters:
    - Bucket size: Max tokens allowed in the bucket.
    - Refill rate: Number of tokens put in bucket each second.
- Based on the use-case - number of buckets will differ.
- Pros:
    - Easy to implement.
    - Memory efficient.
    - Allows burst of traffic as long as token are present.
- Cons:
    - Since only 2 parameters, difficult to tune them properly. ^0DZQ5pFZ

- Similar to Token Bucket Algorithm, but processed at fixed rate.
- Implemented with a FIFO queue.
- When a request arrives:
    - If queue is not fill, request is added to queue.
    - Else request is dropped.
- Requests are pulled from queue and processed at regular intervals.
- Leaking bucket has 2 parameters:
    - Bucket size (Queue size): Max requests stored within queue.
    - Outflow rate: How many requests processed at fixed rate.
- Pros:
    - Memory efficient.
    - Useful for use case where stable outflow rate is needed.
- Cons:
    - Burst traffic may fill up queues causing recent requests to be rate limited
    - Since only 2 parameters, difficult to tune them properly. ^JNnmkMnz

- Timeline divided into fixed time windows and counters assigned for each window.
- Each request increments counter by 1.
- Once counter reaches pre-defined threshold, new requests are dropped until new window starts.
- Pros:
    - Memory efficient.
    - Easy to understand.
    - Can reset the available quota at end of time window.
- Cons:
    - Traffic spike allowed during end of time window, causing more request to go through.

 ^0rPDagA4

- Fixes the issue with Fixed window counter algorithm:
    - More requests allowed at edges of window.
- Keeps track of request timestamps:
    - Timestamps stored in cache.
- When new request comes in:
    - Remove all outdated timestamps (older than current time - time window size)
    - Add timestamp for new request to the log.
    - If log size <= allowed count, request is accepted.
    - Else request is dropped.
- Pros:
    - Rate limiting is accurate.
- Cons:
    - Consumes lot of memory (rejected timestamps are also stored). ^JAzcPnUx

- Not perfect algorithm.
- Combines Fixed window & Sliding window log.
- For a new request - we can calculate no of requests using this formula:
    - Requests in current window + requests in the previous window * overlap percentage of
the rolling window and previous window.
    - Based on this value:
        - if value <= max requests per minute, allow the request.
        - Else drop the request.
- Pros:
    - Smooths out spikes in traffic based on average rate of previous window.
    - Memory efficient.
- Cons:
    - Only works for not-do-strict look back window. ^cxbo551q

- Database:
    - Make use of in-memory cache.
    - Offers 2 commands:
        - INCR: increases stored counter by 1.
        - EXPIRE: sets timer on counter for automatic deletion.

- Rate limiting rules are stored as config files:

        - domain: messaging
        descriptors:
            - key: message_type
                Value: marketing
                rate_limit:
                unit: day
                requests_per_unit: 5

- On exceeding the rate limit - HTTP response code 429 sent.
- The rate limiter returns the following HTTP header to client:
    X-Ratelimit-Remaining: The remaining number of allowed requests within the window.
    X-Ratelimit-Limit: It indicates how many calls the client can make per time window.
    X-Ratelimit-Retry-After: The number of seconds to wait until you can make a request again
    without being throttled.    

-Detailed Design:   ^o3FJqycp

Rate limiter in distributed environments:

- 2 challenges:
    - Race condition
    - Synchronization issue
- Race condition:
    - Issue: concurrent read and update of counter in cache for request count part.
    - Locks can be used to solve this, but significantly slow down the system.
    - 2 strategies followed:
        - Lua scripts
        - Usage of sorted sets data structure
- Synchronization issue:
    - When multiple rate limiters are used - synchronization is a must.
    - Scalable solution is to use a centralised data store across all rate limiters - Redis. ^dizBtsV4
